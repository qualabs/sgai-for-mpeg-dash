# DASH conformance audit — v10.1 (2026-09-25)

**Audit target**: `../output/v10.1-sgai-spec.md`.
**Reference**: the edition declared in
`../context/00-normative-base.md` (ISO/IEC 23009-1:2026, Sixth edition),
primary copy confirmed by `bin/check-normative-base.py` (exit 0), and the
published MPD schema of that edition (`DASH-MPD.xsd`, `DASH-MPD-UP.xsd`
from the edition's public schema package, Annex B).
**Method**: inventory + clause searches against the primary copy +
schema validation of every example + per-construct verdict.

## Scope

Conformance of every construct v10.1 introduces or reuses against the
base specification's schema, extension-point rules, event rules, profile
restrictions (§8.1, §8.2, §8.4, §8.12, §8.14, §8.15) and inherited
attribute semantics (§5.16). Design quality is out of scope.

## Method summary

- **Inventory** built from §2.1, §3.3, §4.7, §4.8, §5.1–§5.10 and the
  annex documents (A–P).
- **Quotation check.** All 107 quoted sentences in chapters 1–8 were
  searched in a whitespace-flattened extraction of the primary copy: 102
  matched directly; the other 5 (Table 57 ERT row, §5.16.4 `@clip` row,
  §5.16.5.2 `@executeOnce`, `@noJump`, `@skipAfter` rows) are split by
  table columns and were confirmed by reading the rows. Control: a known
  sentence ("At least one Adaptation Set shall be present in each Period")
  was found; a fabricated one was not.
- **Clause-number check.** Each quote was located and its enclosing
  clause compared with the cited number. No citation points at a
  different clause. Minor: *"non-negative integer in decimal
  representation"* sits in Table H.1 (§H.2.3); the spec's single cite
  after it and the next quote is §H.2.1.
- **~45 targeted clause reads**: §4.2, §5.2.1, §5.2.3.2, §5.3.1.4,
  §5.3.2.2 Table 4, §5.3.2.6.1–3, §5.8.4.7–9, §5.9.1, §5.10.1,
  §5.10.2.1–2 (Tables 43, 44), §5.10.4.5 (Tables 46, 47), §5.11.3,
  §5.16.1–§5.16.6 (Tables 57, 58, 62, 63), §7.3.1, §8.1, §8.2, §8.4.2,
  §8.12.4.4, §8.13.2.4/2.7, §8.14, §8.15, Annex D.4.6 (Table D.5),
  §H.1–H.2.3, §I.2.3.3, §I.3.1, Table I.4, Table I.5, §L.1, §L.3.4.2,
  Table K.9/K.18, base examples G29-1 and G29-2.
- **Schema validation.** The §5.10 schema was extracted and compiled
  against the base schema. **85 of 85** XML fragments of the spec
  (every `xml` block except the §5.10 schema and the two illustrative
  VAST responses) validate against base + extension schema. The
  validator was shown to discriminate: a bad layout token, a `Click`
  before `RenderableAsset`, a `Candidate` without options, two
  `EventStream`s in one `Candidate`, an out-of-range rectangle, an
  `svta:` child before a DASH child of `Period`, and an MPD without a
  `Period` were all rejected.
- **Rule checks on 72 complete MPDs** (18 main, 9 List, 24
  Single-Period Static, 21 non-linear resolution documents): one
  `EventStream` per scheme/value per Period; non-decreasing Event times;
  unique `Event@id` per stream; `@maxDuration` on every alternative-MPD
  event; no `InsertPresentation` in a dynamic MPD; `RequestParam` implies
  MPD-level `EssentialProperty` `urn:mpeg:dash:urlparam:2025`; SPS rules
  of §8.15.2/§8.15.3; List rules 1, 3, 5 of §8.14; callback streams
  `@value="1"`; non-linear shape (static, Full profile, one `PT0S` Period
  whose only child is `svta:OverlayList`). The checker was run against
  deliberately broken MPDs and reported each defect. One finding (C22).

## Base-standard findings (highlights)

- **Linked-Period merge (§5.3.2.6.3).** The base merge keeps Linked-Period
  `EventStream`, `ServiceDescription` and foreign-namespace children, so
  the List MPD extension content survives resolution (C19, C20, C23); but
  it resolves a same-scheme, same-value stream present in both places by
  **override**, not union (C21).
- **Event identity (Table 44).** `@id` is scoped per scheme/value pair
  across the media presentation, not per Period (C22).
- **Profiles.** `isoff-live:2011` and the Full profile both let a client
  ignore the §5.2.3.2 list, which includes `Period.EventStream` (C44); the
  Full profile applies the §7.3/§7.4 MPD rules, vacuously for the
  non-linear document (C26); the List profile inherits the CMAF profile's
  Period model (C24).
- **Callback and schema.** Table 47 and the XSD (`messageData
  use="prohibited"`) support URL-as-content (C31); the XSD confirms every
  default the spec cites (`maxDuration`, `skipAfter`, `noJump`,
  `executeOnce`, `ImportedMPD@earliestResolutionTimeOffset xs:double
  60.0`) and the absence of a schema default for the event-level
  `@earliestResolutionTimeOffset`.

## Non-conforming items detail

### C21 — Union of the two linear tracking positions

- **Rule.** §5.3.2.6.3 step 3c: *"In case equivalent above elements are
  present in both Linked Period and Imported Period, the elements from the
  Imported Period replace (i.e. override) the elements from the Linked
  Period."* For `EventStream`, equivalence is *"EventStream@schemeIdUri
  and EventStream@value"*.
- **Conflict.** §5.5.2 lets a linear ad carry the callback stream
  *"Inside the sub-MPD's Period, or on the List MPD Period of the ad"* and
  says *"Where both positions of one ad carry a stream, the Player fires
  their union, reduced by §5.5.4."* Both streams have
  `urn:mpeg:dash:event:callback:2015` / `1`, so a base Player keeps only
  the sub-MPD's stream and never fires the List-Period beacons. §1.4
  promises identical behaviour on inherited linear constructs except
  where §4.8.3 records otherwise; §4.8.3 does not record this.
- **Fix.** For the linear family either (a) adopt the base override (the
  sub-MPD stream replaces the List-Period stream) and require the APS to
  put a linear ad's whole schedule in one position, or (b) forbid authoring
  both positions for one linear ad. Keep the union for non-linear
  candidates, where no base merge applies. Annex A already authors one
  position per ad and needs no change.

### C22 — Callback `Event@id` reused across the ads of one List MPD

- **Rule.** Table 44 `@id`: *"specifies an identifier for this instance
  of the event"*; *"Each EventStream element shall not contain two Event
  elements with the same value of Event@id"*; *"The scope of the @id for
  each Event is within the same @schemeIdURI and @value pair over the
  duration of the current media presentation."* The default `@status`
  `repeat` declares *"the event is a repeat of an earlier event with
  identical values of @schemeIdUri, @value, @id and content"*.
- **Conflict.** §5.5.4 scopes de-duplication to *"the Period on a List
  MPD"* and §4.5.13 item 3 obliges a Player to *"fire both of two beacons
  that share an `@id` in two different ads"*. Annex F.3 authors ids `1`
  and `2` in all four Periods of one List MPD and states *"that is
  correct"*; Annex A.3/A.4 produce the same collision after the merge
  (`ad-7731` ids 1–6 on the List Period, `ad-7732` ids 1–5 from its
  sub-MPD). Within one media presentation these Events share scheme,
  value and id while differing in content, so each later one asserts a
  repeat that it is not, and a base Player keying on (scheme, value, id)
  may suppress the impression of every ad after the first.
- **Fix.** For List MPDs, require `Event@id` to be unique per
  (scheme, value) across the whole List MPD, streams merged from sub-MPDs
  included, or omit `@id` on linear beacons; keep the per-candidate scope
  of §5.5.4 for non-linear documents (extension content, outside the base
  rule). Renumber Annex F.3 and Annex A.3/A.4.

## Marginal items detail

### C10 — `@maxDuration` absence on inherited events

The base reads absence as infinity (§5.16.5.2) and the schema supplies
`default="2251799813685247"`. The spec requires the attribute and makes
a Player of this specification present no ad when it is lexically
absent. The departure is recorded (§4.8.3) and the lexical-presence rule
is stated (§5.1.1), so the documents stay valid DASH. What remains
ambiguous: a schema-aware parser that applies attribute defaults cannot
tell absence from the default, and the justification ("what a profile
does", §8.1) fits poorly, because §8.1 NOTE 1 says profiles *"merely
specify restrictions on MPD and Segments rather than DASH Client
behaviour"*, while this rule changes Player behaviour on a document the
base plays. **Clarify**: present it as a restriction on documents this
specification's Player accepts, and add that implementations MUST read
the attribute before schema-default augmentation.

### C17 — Linear failure outcome vs the base's open failure list

§4.5.6 item 4 says a List MPD with candidates *"is not a failed
execution, whatever the Player then does with them"*, because *"the base
condition is media availability after the merge, not renderability on
one device"*. The base list is open: *"The playback of the alternative
presentation cannot start. The reasons for this include (but are not
limited to)"*, and it also names *"Media playback is impossible due to
missing media or initialization segments"*. An ad the device cannot
decode, or whose first segments cannot be fetched (§4.5.16), is playback
that *cannot start*, which under the base is a failed execution that
advances to the next queued event (§5.16.2.2.5). The spec sends it to the
primary content instead, and §4.8.3 does not record this. **Clarify**:
record it in §4.8.3 as a departure for the linear family, or keep the
base outcome (next overlapping linear event) when nothing of a List MPD
can start.

### C24 — Linear empty resolution under the List profile

Table 4 and §8.14 rule 4 support a regular `PT0S` Period with no media,
and §5.16.2.2.6 anticipates *"merge process resulted in no available
media"*. But the List profile *"is an extension of the ISO-BMFF CMAF
Profile"*, and §8.12.4.4 states *"If the Subset element is not present,
the Period contains exactly one CMAF Presentation"*, which an empty
Period does not. Whether that CMAF constraint binds a zero-duration
Period is not settled by the text. **Clarify**: note the reading the spec
relies on (the CMAF Period constraints are vacuous for a zero-duration
Period with no Adaptation Set) and tag it `[inferred]`, or raise it with
the base-standard editors.

### C29 — §5.10 schema says "strict", the schema is lax

The §5.10 intro and §4.6 step 2 correctly say the base-namespace wildcard
in `Candidate` is lax and does not check the element. The paragraph after
the schema says the wildcard admits one base-namespace element
*"validated strictly against the base schema"*. Tested: a `Candidate`
holding an `EventStream` without the required `@schemeIdUri`, an
`EventStream` with an unknown child, and even an `<AdaptationSet/>` all
**validate** against the published schemas. **Clarify**: rewrite that
paragraph to say the element is admitted laxly and checked by §4.6 step 2
(bound to `EventStreamType`); optionally require `xsi:type` so that a
lax validator can check it.

### C41 — The request-type URN and the profile rules

§4.7.5 quotes §I.3.1 up to *"shall be present and have no content"*;
the sentence continues *"unless the scheme is explicity allowed in a
profile (e.g. ISO-BMFF Advanced Linear Profile defined in 8.13)"*. So the
legacy cost it describes (a client ignoring the whole MPD) is not
universal. Conversely, under that profile §8.13.2.7 enumerates *"The
following values may appear in the @includeInRequests attribute"* —
`mpd`, `mpdpatch`, `segment`, `init`, `steering`, `callback`, `altmpd`,
`mpdlink` — and no URN, while Table I.4 in general admits one. A main MPD
declaring `advanced-linear:2025` and carrying
`urn:svta:dash:sgai-resolution:2026` has an ambiguous profile status.
**Clarify**: quote the full §I.3.1 sentence, and state what a Publisher
declaring the Advanced Linear profile does with the URN.

### C44 — The annexes' main-MPD profile lets a client ignore every window

Every annex main MPD declares `urn:mpeg:dash:profile:isoff-live:2011`.
§8.4.2: *"The elements and attributes listed in subclause 5.2.3.2 may be
ignored"*; §5.2.3.2 lists `Period.EventStream` (and
`MPD.EssentialProperty`); §8.1 profile-specific MPD step 5 removes what
*"may be ignored"*. A client conforming to that profile may therefore
drop every SGAI window **and** every inherited linear event. This breaks
no rule (the spec leaves `@profiles` to the Publisher, §5.1), but the
examples model a profile under which the opportunity carrier is optional
to read. **Clarify**: note it in §5.1 or §4.7, and prefer in the examples
a profile that does not list §5.2.3.2 as ignorable (the base's own
alternative-MPD example, G29-1, uses `advanced-linear:2025`).

## Open questions surfaced

- **C24** — whether §8.12.4.4's CMAF Period constraints bind a
  zero-duration, media-less Period of a List MPD. Searched §8.12.4.4,
  §8.12.4.5 and §8.14; no sentence about zero-duration Periods. Searched
  the whole extraction for zero-duration Period rules: only Table 4's
  exception was found (instrument confirmed on that sentence).
- **C41** — whether §8.13.2.7's list of `@includeInRequests` values is
  exhaustive for the Advanced Linear profile. The clause says only *"may
  appear"*.
- **C46** — registration of the `svta` URN namespace identifier: outside
  the base standard, not checked `[inferred]`.

No `[fetch-failed]` item: every construct's governing clause was located.
