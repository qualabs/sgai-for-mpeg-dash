# Spec validation — v7.1 (2026-09-16)

Built against:
- spec: `../output/v7.1-sgai-spec.md` (4761 lines, chapters 1–8 + Annexes A–N + a trailing `## Refinement gaps` table)
- context/ at git SHA: `cb10ae1400493ba4d5fd45f4b5b31a42ec6b694c` (`context/` clean in the working tree; `context-analysis/` carries uncommitted edits, which were read as-is)

Method: independent peer review. Every chapter and every annex was walked
against `../context/01..08,99` and `../context-analysis/`. No MPEG-DASH 6th
edition source was consulted, so every claim this document makes about
ISO/IEC 23009-1 is a claim about what the *spec says*, never about what the
base specification says — see §6, "What could not be verified".

The trailing `## Refinement gaps` table is treated as part of the document
under validation. Where an item in it is still a live defect in the spec
body, it is reported below on its own merits, with its gap-table number
noted for traceability. Where the body has in fact closed it, that is said.

## Gaps (8)

Things a conformant implementer needs in order to ship, for which
`../context/` does not supply enough.

### G-1. No conversion or rounding rule between the slot cap and a candidate's duration

- **Spec sections**: §5.1.3.1 / §5.1.4.1 (`@maxDuration`, `xs:unsignedLong`
  in the parent `<EventStream>@timescale` units) vs §5.2.2.4
  (`<svta:Candidate>@duration`, `xs:duration`) and §5.2.1.1
  (`Period@duration`, `xs:duration`). §4.6.4 compares them.
- **What the context is missing**: R4 states the cap abstractly ("maximum
  duration") and never fixes a timebase. Nothing in `context/` says how a
  timescale-unit integer and an ISO 8601 duration are compared, or which way
  a fractional unit rounds at the cap boundary.
- **What an implementer does today**: guesses. Two conformant Players
  disagree by up to one timescale tick on `drop before play`, which is
  observable: with `timescale="1000"` and a cap of `10000`, a candidate of
  `PT10.0004S` is either dropped or accepted depending on the rounding the
  implementer invented.
- Gap-table #8. Still open in the body.

### G-2. No Player behaviour for a slot authored without `@maxDuration`

- **Spec sections**: §4.3.2 (Publisher obligation), §5.1.1 (`@maxDuration`
  "no in the base schema; **yes** under this specification", base default
  `2251799813685247`), §8.1 row E9.
- **What the context is missing**: R4.1 binds the Publisher and R4.2/R4.3
  bind the Player *given a declared cap*. Nothing in `context/` says what the
  Player does with a manifest that violates R4.1 — and a non-conformant
  manifest is exactly the case a Player meets in the field.
- **What an implementer does today**: picks one of two opposite behaviours —
  inherit the unbounded base default (slot effectively uncapped) or decline
  the slot. E9's "Other actors" column notices the hole and routes it back to
  §4.3.2 rather than answering it.
- Gap-table #4. Still open.

### G-3. `@allowedLayouts` is not bound to the slot family

- **Spec sections**: §3.2 (the "Where it appears" column is prose, not a
  constraint), §5.1.3.1 and §5.1.4.1 (both type the attribute as "tokens…
  each drawn from §3.2"), §4.6.5 (exact-token match).
- **What the context is missing**: R12.2 constrains the *vocabulary* a
  Publisher may draw from; it says nothing about which tokens are admissible
  on which slot family. There is no requirement that ties a family to a token
  subset.
- **What an implementer does today**: a Publisher may list `pause-ad` on an
  overlay slot and `overlay-corner` on a pause-trigger window; both pass every
  check the spec states. An APS emitting a `pause-ad` option for an overlay
  slot is not caught by §4.5.4 either. The Player renders it, because both
  checks in §4.6.5 pass.
- Gap-table #7. Still open. See Flag F-1.

### G-4. The hybrid break on a single-decoder device is decided twice, oppositely

- **Spec sections**: §7.5.4 ("A device with overlay surfaces but a single
  decoder **presents the linear portion alone** when the overlay option needs
  to be composited on top of the linear ad's video"), §8.4 (chapter 8 is
  declared **non-normative** at §8: "this specification decides neither,
  because both are properties of the device"), Annex D.5 D3/D4 rows
  (*Informative*).
- **What the context is missing**: `context/04-use-cases.md` UC-04 "Notes /
  open questions" states the question explicitly and says *"the spec must
  declare it explicitly"*. `context/` does not decide it, and R3.2 requires a
  defined behaviour for every (device class × opportunity type) pair.
- **What an implementer does today**: reads §7.5.4 as the answer and §8.4 as
  a denial that there is one. The two are in the same document and disagree
  about whether an obligation exists.
- Gap-table #5, restated: the gap table frames this as "stated only in the
  non-normative §8.4", which understates it — §7.5.4 *does* state it, in a
  chapter that is not marked non-normative, and that is the contradiction.

### G-5. R10.3's Positioning Templates section does not exist

- **Spec sections**: none. `grep -n -i "positioning template"` over
  `../output/v7.1-sgai-spec.md` returns one hit, inside the `## Refinement
  gaps` table (line 4753); the same grep over `../context/` returns four hits,
  which is what proves the instrument searches.
- **What the context is missing**: nothing — R10.3 is explicit: position
  semantics inside a layout "MUST be expressed via the Positioning Templates
  section using HTML5 / CSS primitives". The spec instead states (§1.2) that
  positions "are not expressible in spec-level attributes" and stops there.
- **What an implementer does today**: has no spec-side answer for where an
  `overlay-corner` sits, and no answer at all for an `image` form, which
  carries no HTML/CSS surface on which to express one. The IAB normative
  reference of §3.2 inherits a *size* bound (25 %, 60 %), not a position.
- Gap-table #14. Still open, and it is an unmet document-level MUST rather
  than a soft gap.

### G-6. `linear` on a non-linear slot has no declared primary-timeline semantics

- **Spec sections**: §3.2 (`linear` is admissible "as the full-screen
  takeover offered as a last-resort presentation option on a non-linear
  candidate"), §5.3.3, §5.3.7.3 last row, §6.1, Annexes C/I option 4.
- **What the context is missing**: UC-09 option 4 describes the behaviour
  ("the primary content stops, the ad plays, the primary content resumes")
  but no requirement says which resume semantics apply. A linear slot gets
  them from `<InsertPresentation>` (`@returnOffset` absent, timeline held) or
  `<ReplacePresentation>` (`@returnOffset`, timeline advanced); an overlay
  slot's `<svta:OverlayPresentation>` carries neither attribute.
- **What an implementer does today**: invents it. Two Players resume the
  primary content at two different positions after the same takeover, and
  nothing in the document distinguishes them. See Actionable TODO T3 for the
  narrower contradiction this gap sits behind.

### G-7. `@executeOnce` has no meaning on a pause-trigger window

- **Spec sections**: §5.1.4.1 (`@executeOnce`, "As in §5.1.1"), §5.1.1
  ("When `true`, the event executes at most once in the session").
- **What the context is missing**: `context/` does not mention
  `@executeOnce` at all, and the pause-trigger construct is the one place
  where "the event executes" has no timeline referent — §5.1.4 states
  explicitly that the window is declared on the timeline while the trigger
  fires off it.
- **What an implementer does today**: picks between "the window opens once"
  (in which case `@executeOnce` is inert, since a window opens once anyway)
  and "one pause ad per session" (in which case a viewer who pauses three
  times inside the window sees one ad on one Player and three on another).
  Both readings are available from the text.

### G-8. The ClickThrough carrier is not interoperable on the linear path

- **Spec sections**: §5.6 "Note on profile signalling" — a `ListMPD` whose
  `@profiles` names only `urn:mpeg:dash:profile:list:2024` "therefore has its
  `<svta:Click>` removed by that procedure, and a client bound to the list
  profile alone is entitled to drop it". §2.1 mints no linear SGAI profile
  URI. Annexes A.4, B.3, F.3 all declare the list profile alone.
- **What the context is missing**: R28 requires the carrier to be "normative
  and interoperable… so that every conformant Player reads them the same
  way", and R28.2 makes reading it a Player MUST. `context/06` fixes the URI
  pattern but no requirement asks for a linear-family profile URI, and
  `context/` gives no way to satisfy R28 on the `ListMPD` path.
- **What an implementer does today**: fails R28 silently on every linear ad,
  or mints a private profile URI (which `context/06` forbids outside the SVTA
  namespace). The spec states the consequence and leaves the requirement
  unmet.
- Gap-table #21 characterises this as "§5.6 now states the consequence" —
  stating a consequence is not satisfying R28.1/R28.2, so the defect stands.

## Edge cases (7)

Boundary conditions `../context/04-use-cases.md` does not contemplate that
the spec must nonetheless handle.

### EC-1. Several candidates in one non-linear document: a sequence, or alternatives?

- **Trigger**: an Overlay Resolution Document carrying two or more
  `<svta:Candidate>` elements, where the first renders successfully.
- **Why it matters**: §4.6.7 says "when the resolution document declares more
  than one **candidate** for one slot, the Player presents them one after
  another… each starting when the previous one ends" — a *sequence*. §4.6.6
  says "When no option on a candidate is satisfiable, the Player advances to
  the **next candidate**" and §3.1 defines a candidate as one of a set among
  which "the selection sense… applies to the non-linear document" — a set of
  *alternatives*. The two readings give opposite outcomes for the same
  document: one ad or three. Annex C.7 and T-P7 assume the sequence reading;
  §8.1 rows E6 and E9 assume the alternatives reading.
- **Responsible actor**: Player. `context/` is silent — R14 speaks of
  "forms", a word the syntax chapter never binds to a construct, so neither
  reading can be excluded.
- Gap-table #1 / #13. Live, and the highest-leverage defect in the document.

### EC-2. Does the slot cap accrue while a non-linear form is suspended or paused?

- **Trigger**: an overlay is rendering, the viewer pauses inside a pause-ad
  window (§4.6.9), the overlay is suspended for 40 s of wall clock, and the
  viewer resumes.
- **Why it matters**: §4.6.4 enforces `@maxDuration` against "actual rendered
  length". Annex H.3 shows the overlay *window* freezing with the
  presentation time, but the *cap* is a separate quantity and the spec never
  says whether suspended time counts against it. A 30 s cap either allows
  30 s of visible overlay across the pause or 30 s minus the suspension.
- **Responsible actor**: Player. `context/` silent: R4 says "actual rendered
  length" and UC-08 tracks only the window clock.
- Gap-table #10. Live.

### EC-3. A `200` resolution document of the wrong family for the slot

- **Trigger**: an overlay slot's `@uri` returns a well-formed, schema-valid
  `ListMPD`; or a linear slot's returns an Overlay Resolution Document.
- **Why it matters**: §4.5.1 binds the APS but no row of §8.1 covers the
  Player side. E3 is scoped to "not well-formed XML, an unknown root element,
  or fails schema validation" — a `ListMPD` is none of those. E5 requires
  "carries no candidates" — a `ListMPD` with Periods carries ads, just not the
  kind this slot can use. The window is therefore neither accessible-and-empty
  nor an access failure, so §4.6.8 cannot decide whether the fallback chain is
  tried.
- **Responsible actor**: Player. `context/` silent.
- Gap-table #9. Live.

### EC-4. A pause inside a pause-trigger window while a linear ad occupies the screen

- **Trigger**: a hybrid or plain linear break at `presentationTime` T, a
  pause-trigger window spanning T, and the viewer pauses during the linear ad.
- **Why it matters**: §4.6.9 arbitrates pause-ad against overlay and §8.7
  covers an overlay window and a pause-trigger window at the same position.
  Neither covers a pause-ad opportunity opening while a *linear* ad is
  playing. R22's single-active-form bound does not apply (a linear ad is not
  a non-linear form), so nothing forbids compositing the pause ad over the
  paused linear ad — and nothing authorises it either. Whether the linear
  slot's cap keeps accruing is EC-2 again, on a different surface.
- **Responsible actor**: Player. `context/` silent: UC-05 and UC-08 both
  assume the primary content is what is paused.
- Gap-table #15. Live.

### EC-5. The pause-ad video form on a single-decoder device

- **Trigger**: a pause-ad candidate whose only option is `form="video"`, on
  D3, D4 or D5.
- **Why it matters**: §5.3.7.3's `pause-ad`/`video` row gives a decoder count
  of "1 (the primary content is paused and holds its frame; on a device that
  cannot re-task the decoder, 2)" and then a "Satisfiable on" of **D1, D2**.
  If the count can be 1, D3 and D4 satisfy it; the two columns of one row
  disagree, and the paragraph directly beneath the table, §7.5.5, §8.4 and
  Annex E.4 all say the single-decoder case is a live possibility the device
  decides. A Player implementing the table skips an option the prose says it
  may render.
- **Responsible actor**: Player. `context/` (UC-05 D1) says *"Because the
  primary is paused (no concurrent decoding needed for the primary), even
  single-decoder devices can render a video form here"*, so the prose is the
  context-grounded reading and the table's column is the error.
- See Actionable TODO T1.

### EC-6. Beacon `@id` uniqueness across candidates

- **Trigger**: two candidates in one Overlay Resolution Document, each
  carrying a callback `<EventStream>` whose `<Event>@id` values start at 1.
- **Why it matters**: §5.5.2's de-duplication rule fires a beacon once when
  two streams carry "beacons that share an `@id`, or the same URL at the same
  `presentationTime`". With per-candidate numbering restarting at 1, that rule
  suppresses the second candidate's impression beacon. §5.5.1 makes `@id`
  required but scopes its uniqueness nowhere; §5.2.2.4 scopes `<svta:Candidate>@id`
  "unique within the document" and §5.2.1.1 does the same for `Period@id`, so
  the omission is visible against its own neighbours.
- **Responsible actor**: APS (authoring) and Player (de-duplication).
  `context/` silent.

### EC-7. Two overlapping windows of the same family whose `@allowedLayouts` differ

- **Trigger**: Annex L's chain, but with window 1202 allowing a token set
  that window 1201 does not.
- **Why it matters**: §4.6.8 says the Player "resorts to a subsequent one
  only when it cannot access the first window's resolution document" and
  Annex L.3 path 2 says the Player "validates its candidates against window
  1202's **own** constraints". That is the right answer, and it is stated
  only in an *Informative* annex — §4.6.8 itself never says which window's
  constraints bind the candidates served from the fallback. A Player that
  carried the first window's `@allowedLayouts` forward is not contradicted by
  any normative sentence.
- **Responsible actor**: Player. `context/` (UC-12) is silent on whose
  constraints apply to the fallback's candidates.

## Ambiguities (6)

### A-1. Scheme URIs carry a segment the naming policy does not admit

- **Context passage**: `context/06-naming-and-namespaces.md:22` — "New event
  schemes introduced by this spec MUST use the year-pinned pattern under the
  SVTA Ads WG namespace: `urn:svta:dash:<construct>:<year>`", with the
  illustrative examples `urn:svta:dash:sgai-overlay:2026` and
  `urn:svta:dash:sgai-pause-trigger:2026`.
- **Two readings**: (a) `<construct>` is a single segment, so the pattern has
  exactly four colon-separated parts; (b) `<construct>` may itself contain
  colons, so a `event:` / `profile:` classifier is admissible.
- **What the spec assumed**: (b). §2.1 publishes
  `urn:svta:dash:event:sgai-overlay:2026`,
  `urn:svta:dash:event:sgai-pause-trigger:2026` and
  `urn:svta:dash:profile:sgai-overlay-list:2026`. The element namespace
  `urn:svta:dash:sgai:2026` follows (a). The spec does not declare the
  divergence, which `context/06` would require a reader to notice on their own.
- **A tighter context sentence**: "…the pattern
  `urn:svta:dash:<kind>:<construct>:<year>`, where `<kind>` is one of `event`
  or `profile`, and `urn:svta:dash:sgai:<year>` for the XML namespace."
- Gap-table #16. The spec is the better half; `context/06` is the half to change.

### A-2. "Overlay" names a layout token, a slot family, a document class and a profile URI

- **Context passage**: `context/99-glossary.md` — "**Overlay**: umbrella term
  for any non-linear ad surface", while R12 also uses `overlay` as one of four
  ad types with its own named placements.
- **Readings**: on an Overlay Resolution Document for a pause-trigger window
  whose `@allowedLayouts` is `pause-ad`, "overlay" means the family; in
  `@layout="overlay"` it means one spatial arrangement; in
  `urn:svta:dash:profile:sgai-overlay-list:2026` it means the document class.
- **What the spec assumed**: the umbrella reading for the document, the
  profile URI and `<svta:OverlayList>`, and the narrow reading for the token.
  §5.2.2.2's note (added at v7.1) now says so explicitly, which removes the
  reader-facing ambiguity without removing the overload.
- **A tighter context sentence**: give the umbrella concept its own word in
  `context/99-glossary.md` — "non-linear surface" — and reserve "overlay" for
  the IAB ad type.
- Gap-table #17. Partially closed by the note; the wire-format names stand.

### A-3. `@maxDuration` on `<InsertPresentation>`: required, with a default

- **Context passage**: `context/03-requirements.md:297` (R4.1) — "The
  Publisher MUST declare a maximum duration on every ad slot".
- **Readings**: §5.1.1's row reads "Required: no in the base schema; **yes**
  under this specification" and, in the same row, "Default:
  `2251799813685247` (unbounded)". Either the attribute is required and the
  default is unreachable, or it is optional and the default applies. A
  conformance checker cannot decide whether an absent `@maxDuration` is a
  violation or a value. §5.1.3.1 and §5.1.4.1 have the same attribute with
  "Required: yes" and no default, so the spec answers the question two ways
  for two slot families.
- **What the spec assumed**: required, with the base default retained for
  reference — the only reading consistent with §4.3.2.
- **A tighter context sentence**: R4.1 already says it; the fix is spec-side,
  but which way (strike the default, or downgrade to SHOULD with the default
  as the fallback) changes what a checker reports. See Flag F-4.
- Gap-table #3.

### A-4. Splitting the double box into two tokens makes an advertiser's background Publisher-gated

- **Context passage**: `context/03-requirements.md:750` (R26.1/R26.2) — the
  background element "MAY fill those bands; when none is present they render
  as black", and the Player "MUST place it in the uncovered bands" when "the
  advertiser supplies" one.
- **Readings**: (a) the presence of a background is a property of the
  creative, decided by the advertiser at render time; (b) it is a property of
  the layout, and therefore of the token, and therefore gated by the
  Publisher's `@allowedLayouts`.
- **What the spec assumed**: (b). §3.2 mints `squeezeback-double-box` and
  `squeezeback-double-box-with-background` as separate tokens, §4.6.5 matches
  by exact token, and §3.2 states "`overlay` does not implicitly admit
  `overlay-corner`". Consequence: a Publisher who lists only
  `squeezeback-double-box` makes an advertiser-supplied background
  unrenderable — an outcome R26.2 does not contemplate, since it enumerates
  only "supplied" and "not supplied".
- **A tighter context sentence**: R26.1 should say whether the background's
  presence is Publisher-gateable, or state that a Publisher permitting the
  double box permits it with or without a background.
- Gap-table #2. The vocabulary decision is Flag F-9's neighbour and is routed
  to §5.b; the carrier's undeclared cardinality, which is separable, is
  Actionable TODO T4.

### A-5. `pause-ad` maps to two IAB placements, not one

- **Context passage**: `context/06-naming-and-namespaces.md:113` — "the
  layout vocabulary MUST map 1:1 to IAB-defined ad-type values"; R12.1 —
  "each mapped to its IAB definition".
- **Readings**: (a) one token per IAB *type*; (b) one token per IAB *visual
  placement*.
- **What the spec assumed**: both, in different rows. §3.2 splits the
  Squeezeback type into three tokens by placement (reading b) and collapses
  Pause Ad's two placements — "Fullscreen or Partial Screen" — into the single
  token `pause-ad` (reading a). Which surface applies is then deferred to
  §7.5.5 as "a property of the option the Player selects", with no attribute
  carrying it, so a Publisher cannot permit a partial pause ad and forbid a
  fullscreen one.
- **A tighter context sentence**: R12 should state whether the token axis is
  the type or the placement, once, and apply it to every entry.

### A-6. An image form's declared duration: presentation timeline or wall clock?

- **Context passage**: `context/03-requirements.md:636` (R19) — "`duration`
  remains expressed on the presentation timeline (the single source of truth
  per DP-1.2); the wall-clock on-screen length is derived from it".
- **Readings**: for a `video` form the presentation timeline is the media's
  own; for an `image` or `html` form there is no media, and §5.5.3 anchors
  the origin at "the moment the asset becomes visible". A reader may take the
  declared `@duration` as wall clock (the image is on screen for 15 s) or as
  presentation time (at 2× it is on screen for 7.5 s).
- **What the spec assumed**: presentation time — §8.6 says "the candidate's
  declared `@duration` is the length" and §4.6.12 applies
  `duration / playback_speed` to "every ad form". The consequence, that a
  still image disappears in half the wall-clock time when the viewer is
  watching at 2×, is never stated and is counter-intuitive enough to warrant
  saying.
- **A tighter context sentence**: R19.3 should name the non-media forms
  explicitly, since they are the case where "the presentation timeline" has
  no media to anchor it.
