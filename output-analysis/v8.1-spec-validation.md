## Method note

**The population came from the script, not from a count of my own.**
`bin/check-promotable.py --population` emitted **168** units — 123 criteria,
31 prose obligations, 14 use cases — and the map below walks exactly those ids.

**Three instructions in `validate-spec.prompt` are stale, and I did not obey
the first.**

1. **§4.1's acceptance test inverts the correct answer.** The prompt states that
   UC-14 was added after the newest spec was generated, that the spec does not
   walk it, and that a run not reporting `UC-14` as `gap` has not walked the use
   cases. **UC-14 is walked**: `../output/v8.1-sgai-spec.md` carries a dedicated
   **Annex N — A non-linear ad over a replacement that is not advertising**
   (L7279–L7556), with a per-device-class table at **N.8** (L7541–L7556) whose
   five rows match `context/04-use-cases.md` L1587–L1596 one for one, plus the
   spec-body walk at **§7.5.9** (L3010–L3024). `context-analysis/uc-coverage-matrix.md`
   also carries a UC-14 row, so the pre-spec stage sees it too. I report the
   disposition I found (`met`) and flag the instruction: as written it manufactures
   a false `gap`, and a run that reports the truth appears to have failed the
   step's own test. **Fixing the prompt is out of this step's scope; it is
   reported, not fixed.**
2. **§4.2 says 17 criteria carry no RFC 2119 keyword. The number is 23** (list in
   A-5), measured with the same criterion-block parse the population script uses.
3. **§4.2 says 29 criteria have `spec document` as the actor.** I did not rely on
   that figure either; the `Kind` column below is assigned per unit from the

**One thing the population does not see.** The script's modal regex catches
`MUST`/`MUST NOT`/`SHALL`/`SHALL NOT`/`REQUIRED` only, so a `SHOULD` or `MAY`

*"Implementations SHOULD reuse the existing DASH callback event scheme"*
(`03-requirements.md` L1430) is therefore walked only through its criterion
R6.2, which is where the over-strengthening of A-2 shows up.

**There is no verdict for a modal that arrived stronger than its source.** The

found (R6.2, `SHOULD` → `MUST`) is recorded as `contradicted` with the direction
stated in its Notes, rather than being lost between the verdicts.

## Gaps (7)

Things a conformant implementer needs and `context/` does not supply enough
information for.

**G-1. The concrete media types of the `image` carrier are not in the inputs.**
R15 defines the `image` carrier as *"concrete formats defined by IAB ad
templates"* (`03-requirements.md` L552). The spec fixes them as
`image/jpeg`, `image/png`, `image/webp` (§3.3 L358, §5.3.2 L1899). Neither
`context/` nor `context-analysis/` names that set: the only concrete image list
in the inputs is `iab-ad-templates.md` L45, *"Creative is static image (jpg, png,
gif)"*, and it belongs to **In Scene Ads**, which §3.2 places out of scope. The
spec's set therefore **adds** `webp` and **drops** `gif` with no source.
Instrument check on the negative: `grep -rn "webp"` over `context/` and
`context-analysis/` returns nothing, while the same grep for `png` returns the
L45 hit, so the search finds what is there.
*Implementer today*: guesses. An APS emitting `image/gif` and a Player rejecting
it are both defensible.
→ **5.c**

**G-2. What the slot cap bounds on a pause window is undefined in `context/`.**
R4.1 obliges every slot to declare a maximum duration (L349–L351); R31.2 says
that on a pause slot the cap *"MUST NOT be interpreted as bounding the duration
of a pause slot"* and *"on a pause slot it bounds neither"* (L442–L446). So a
mandatory declaration is left with no stated meaning. The spec fills it:
`@maxDuration` on a pause-trigger window is *"Maximum display duration of **one**
pause ad before automatic dismissal"* (§5.1.4.1 L1508, repeated §4.6.4 L725).
That reading is reasonable and it is **not in the inputs**.
*Implementer today*: a Publisher cannot tell whether the value it must write
does anything.
→ **5.c**

**G-3. A zero `@maxDuration` on a pause-trigger window.** R4.7 adopts the base
specification's rule that a zero cap means the event is not executed
(L376–L380) — a rule about a **playhead-executed** event. A pause window is not
executed by the playhead (R31), so whether a zero cap suppresses the resolution
request, or bounds a pause ad at zero display time, is unstated. The spec's
§8.1 E6 states the general zero rule (*"With zero, the opportunity does not
fire"*, L3047) without separating the pause family.
*Implementer today*: the APS observes the difference — one reading issues a
request and the other does not.
→ **5.c** (same item as `Refinement gaps` #6)

**G-4. No retry, backoff or deadline for the resolution request.** `context/`
states none, and the spec says so rather than inventing one: §8.1 E1,
*"**Open**: this specification fixes no retry count, backoff or deadline"*
(L3042), and E5, *"no Player response for a document that lands after the window
is over"* (L3046).
*Implementer today*: picks its own, and two conformant Players spend a
Publisher's fallback windows differently.
→ **5.c**

**G-5. A carrier outside the admissible set that the device can nevertheless
render.** R15.3 is permissive only — the Player *"MAY skip"* (L569) — so nothing
says what happens when it does not skip. The spec carries the hole as an open
point: §8.1 E9, *"**Open**: for a carrier outside the admissible set that the
device *can* nevertheless render, this specification states no obligation either
way"* (L3050).
*Implementer today*: renders a non-conformant creative or does not, both
conformant. `context-analysis/error-semantics.md` marks the same row
**UNDEFINED**.
→ **5.c**

**G-6. No "unrestricted" value for the allowed-layouts declaration.** R12.2
obliges a Publisher to draw names from the enumerated set (L526–L529) and says
nothing about admitting all of them. The spec closes it by construction —
§8.1 E8, *"**Open**: this specification defines no 'unrestricted' value for
`@allowedLayouts`, so a window admits exactly the tokens it lists"* (L3049) —
which makes every Publisher restate the whole set to mean "no restriction", and
makes a slot silently narrow when a later edition adds a token.
*Implementer today*: enumerates, and the enumeration goes stale.
→ **5.c**

**G-7. Nothing scopes a baseline linear break to Players that predate this
specification.** UC-07 assumes one exists: the VOD fallback break *"is authored
unconditionally for VOD and is simply ignored by current Players that take the
richer SGAI path"* (`04-use-cases.md` L816–L818). No construct in `context/`
produces that behaviour, and the spec states the consequence instead of the
assumption: *"This specification carries no construct that scopes a break to
Players that predate it, so the Publisher's two options are to author the break
and accept that a current Player composes both, or to author no break and accept
the loss on the older Players"* (§4.7.7 L1230–L1233).
*Implementer today*: a Publisher following UC-07 double-serves every current
Player. See UC-07's row and A-8.
→ **5.c**

## Edge cases (7)

Boundary conditions `../context/04-use-cases.md` does not contemplate and a
deployable spec meets.

**EC-1. A once-per-session pause window whose document declares `repeat`.**
*Trigger*: `@executeOnce="true"` on a `<svta:PauseAdPresentation>` (§5.1.4.1
L1511) together with `@onCandidatesExhausted="repeat"` (§5.2.2.3 L1748).
*Why it matters*: `repeat` re-presents the sequence for as long as the pause
lasts; the window is consumed when a pause ad *"begins rendering"* (§4.6.12
L951–L953). Either the second presentation is a second pause ad the window
forbids, or "at most one pause ad" counts presentations of one candidate as one.
*Responsible*: the Player, and `context/` is silent — R32 and R34 never mention
each other.
→ **5.b** (`Refinement gaps` #1, still open)

**EC-2. What a once-per-session bound means on an overlay window carrying
several candidates.** *Trigger*: `@executeOnce="true"` on
`<svta:OverlayPresentation>`, which §5.1.3.1 L1436 defines as *"the window yields
at most one overlay presentation for the session"*, against R14's in-slot
sequence of candidates.
*Why it matters*: "one presentation" is one candidate or one whole sequence, and
the two differ by every candidate after the first.
*Responsible*: the Player. R34 defines the attribute for the pause family only,
so either reading adds a requirement.
→ **5.b** (`Refinement gaps` #2, still open)

**EC-3. The de-duplication key across the two carrier placements one candidate
may use.** *Trigger*: a `video`-form candidate carrying a tracking
`<EventStream>` inside `<svta:Candidate>` **and** another inside its sub-MPD
`<Period>`, which §5.5.2 L2248 permits; the Player *"fires the union, with
beacons sharing an `@id`, or carrying the same URL at the same
`@presentationTime`, fired once"* (L2251–L2254).
*Why it matters*: `@id` is unique per `<EventStream>` and not across two, and the
same beacon can carry different `@id`s in the two carriers and different
`@timescale`s for one presentation time. The union is then either
over-counted or silently collapsed.
*Responsible*: the Player and the APS; `context/` R6.5 scopes the key to the
candidate without normalising across carriers.
→ **5.b** (`Refinement gaps` #3, still open)

**EC-4. A live pause that outlives the time-shift buffer.** *Trigger*: a pause
inside a pause-trigger window on live content, lasting longer than
`MPD@timeShiftBufferDepth`.
*Why it matters*: R25.1 promises a freeze *"for the full duration of the pause"*
(L1016–L1019) and no Player can deliver it past the buffer. The spec states the
bound the requirement lacks — *"Where the pause outlives
`MPD@timeShiftBufferDepth`, the freeze ends with the buffer"* (§4.6.17
L1034–L1036), with the base specification's clipping rule quoted.
*Responsible*: the Player; `context/` is silent, which is why R25.1 and R25#p1
are `partial` below.
→ **5.c** (`Refinement gaps` #15, still open)

**EC-5. A non-linear presentation that would outlive the `<Event>@duration`
declaring its window.** *Trigger*: a candidate whose duration fits the cap while
the window's own `@duration` ends sooner.
*Why it matters*: R14.2 enforces the cap *"when the cumulative duration would
exceed the slot's opportunity window"* (L1169–L1173), conflating two different
bounds — the cap and the window. The spec enforces the cap (§4.6.7 L805–L808)
and never says what the window's end does to a presentation already on screen.
*Responsible*: the Player; `context/` conflates the two.
→ **5.c** (`Refinement gaps` #4 and #14, still open)

**EC-6. A hybrid break whose linear portion declares `@clip="false"`.**
*Trigger*: §5.1.5's two events at one presentation time (L1538–L1543), the linear
one with `@clip="false"`, which the base specification lets terminate at
`PRTA + APDmax` — later than scheduled.
*Why it matters*: the concurrent overlay's window ends where the Publisher
declared it, so either the overlay's window is extended to match the take-over
or the composition the use cases describe ends mid-take-over.
*Responsible*: the Player; UC-04 does not vary `@clip`.
→ **5.b** (`Refinement gaps` #5, still open)

**EC-7. An overlay window and a pause-trigger window that the Publisher intends
to fill from one resolution.** *Trigger*: UC-08's own ad response, which resolves
the pause slot separately *"unless the Publisher's MPD signals that the overlay
candidate doubles as the pause-ad candidate"* (`04-use-cases.md` L878–L881).
*Why it matters*: no such signal exists. `<svta:PauseAdPresentation>` carries
`@uri`, `@maxDuration`, `@allowedLayouts`, `@earliestResolutionTimeOffset` and
`@executeOnce` and nothing else (§5.1.4.1 L1505–L1511), and Annex H issues two
independent requests (H.4 L5436–L5577). A Publisher following UC-08 pays for two
decisions where it expected one.
*Responsible*: the Publisher and the APS; `context/` names a mechanism it never
defines.
→ **5.c**

## Ambiguities (10)

**A-1. R4.2 and R31.2 disagree about which families the cap bounds by cumulative
duration.** R4.2: *"Where the cap bounds cumulative duration — the non-linear
families, and linear insertion — the Player MUST stop rendering …"*
(`03-requirements.md` L352–L355). R31.2: on a pause slot the cap *"bounds
neither"* (L442–L446). Pause is a non-linear family, so the two cannot both hold.
*Readings*: (a) "the non-linear families" means overlay only; (b) it includes
pause and R31.2 is the exception.
*The spec assumed (a)*: §4.6.4's table gives `Pause | **Nothing**` (L725) and
applies the cumulative rule to overlay and linear insertion (L720–L724, L733).
*Tighter sentence*: in R4.2, replace *"the non-linear families"* with *"the
overlay family"*, and add *"; on a pause slot the cap bounds neither (R31.2)"*.
→ **5.c** (`Refinement gaps` #9, still open)

**A-2. R6.2, R6.3, R13.1 and R13.4 state four different forces for one
tracking-carrier rule.** R6.2: implementations *"SHOULD"* carry beacons on the
callback scheme (L1450–L1452). R6.3: a new carrier *"MAY be introduced only when
the callback scheme cannot express the required semantics"* (L1455–L1458).
R13.1: the APS *"MUST express them using DASH callback events (or an equivalent
baseline DASH construct)"* (L1497–L1503). R13.4: *"reuse of the DASH baseline
callback mechanism is mandatory"* (L1512–L1514).
*Readings*: (a) a recommendation with a documented escape hatch; (b) an
obligation with one permitted alternative; (c) a hard requirement on one scheme.
*The spec assumed (c)*: §4.5.6, *"Beacons MUST be `<Event>` entries inside an
`<EventStream>` of scheme `urn:mpeg:dash:event:callback:2015`"* (L635–L636), and
§5.5 L2190, *"This specification introduces **no** tracking scheme of its own."*
R13.1's alternative and R6.3's condition both disappear, and R6.2's `SHOULD`
arrives as a `MUST`.
*Tighter sentence*: pick one force in `context/` and make the other three cite
it — if (c) is intended, R6.2 becomes *"MUST"* and R6.3 is deleted or restated as
a rule for a future edition.
→ **5.c** (`Refinement gaps` #7 and #10, still open; drives R6.2's
`contradicted` row)

**A-3. R1.3 forbids what R4.10 mandates.** R1.3: the specification *"MUST NOT
alter or override the semantics of any pre-existing MPEG-DASH 6th edition
construct"* (L143–L145). R4.10 requires reading an absent `@maxDuration` as "no
ads from this slot", where the base specification reads it as infinity — and
says so itself (R4.8, L381–L389).
*Readings*: (a) narrowing which documents conform is not altering semantics, so
both hold; (b) changing what an absent attribute means is altering semantics, so
R4.10 breaks R1.3.
*The spec assumed (a)* and flagged it: §4.3.2, *"This is a **deliberate
narrowing** … The narrowing restricts which documents conform and changes no
construct's semantics, which is what a profile-style restriction does"*
(L485–L492), plus the blockquote *"This position diverges from the base
specification and is open"* (L762–L767).
*Tighter sentence*: in R1.3, add *"Restricting which documents conform, without
changing what a construct means where it is present, is not an alteration for
the purposes of this criterion (R4.8)."*
→ **5.c** (`Refinement gaps` #8 and #13, still open; drives R1.3's
`contradicted` row)

**A-4. R26.1's "composition attribute of the slot / layout" is read two ways.**
R26.1: the background element *"MUST be carried as a composition attribute of the
slot / layout, not as a separate presentation option (R5)"* (L1045–L1047).
*Readings*: (a) it hangs off the **slot**, so one background serves every option;
(b) it hangs off the **layout of one option**, so each option carries its own.
*The spec assumed (b)*: `<svta:BackgroundElement>` is a child of the
`<svta:RenderableAsset>` whose `@layout` is
`squeezeback-double-box-with-background` (§5.3.7.2 L2063–L2065). Annex J shows
what that costs: options 1 and 4 are the same form and creative and *"differ in
composition and not in creative"* (L6195–L6199), so the background does become an
axis the Player walks, which (a) exists to prevent.
*Tighter sentence*: say which host carries it — *"as an attribute of the slot
declaration"* or *"as a child of the presentation option whose layout names a
background"*.
→ **5.c** (`Refinement gaps` #12, still open; drives R26.1's `partial` row)

— in the MPD, not inferred — which is what R2.1 says and what §4.3.1's second
sentence supports; (b) the `MUST` governs **which** constraints exist, making a
resolution-timing bound and a once-per-session bound mandatory on every slot.
*The spec's own syntax tables assume (a)*, so the two sites disagree and (a) is
the one `context/` carries: R2.1 lists *"max duration, opt-in policies, layout
templates"* and no timing bound (`03-requirements.md` L165–L168).
*Tighter sentence*: the wording in Actionable TODO T2.
