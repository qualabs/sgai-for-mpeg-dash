# DASH conformance audit — v8.1 (2026-09-18)

**Audit target**: `../output/v8.1-sgai-spec.md` (7816 lines).
**Reference**: the edition declared in `../context/00-normative-base.md` —
ISO/IEC 23009-1:2026, Sixth edition, 2026-07. The primary copy was opened
and its `sha256` matched the declaration
(`a7274eb244d916285f76c3a08c806ec07481968e1e771820eba58370b64be100`);
`bin/check-normative-base.py` exits 0 against the same file.
**Method**: inventory + clause searches against the primary copy + **schema
validation of every XML example against the Annex B schema** +
per-construct verdict.

## Scope

Every construct the specification introduces or modifies: scheme URIs and
namespaces, new elements in `urn:svta:dash:sgai:2026`, baseline elements
reused at new positions, attribute-use narrowings on baseline elements,
the two resolution-document shapes, the sub-MPD binding, and the
`PlayList` metric declaration. This is conformance to the base
specification, not design review.

## Method summary

- Inventory built from chapters 2, 4.7, 5.1–5.9, the build-notes block, and
  every XML example in the annexes.
- 34 clause searches against the primary copy. Each verdict below quotes
  the governing sentence, not only its number. Searches ran against a
  whitespace-flattened extraction so a phrase spanning a line break still
  matches; the base standard's tables interleave the Use/Default column
  mid-sentence, which is why two searches returned zero until reworded.
- **Annex B was reached.** The primary copy carries only the pointer —
  *"The schema of the MPD for this document is provided at:
  https://standards.iso.org/iso-iec/23009/-1/ed-6/en (DASH-MPD.xsd)"*
  (DASH Annex B) — and that location serves `DASHSchema-6th-Ed.zip`
  (HTTP 200, 67 266 bytes), containing `DASH-MPD.xsd`
  (sha256 `81387113dcf41682d8874cdd104157ed8112b4b212c4632922d46cccc84c1615`,
  header comment `<!-- 6th Ed. final -->`). Every schema claim below is
  read from that file rather than inferred, and the `[inferred]` tags the
  candidate carries on schema questions are now unnecessary.
- **All 49 full-MPD examples in the candidate were validated against that
  schema.** 47 valid, 2 invalid — both on the same construct (finding N1).
  The validator was shown to work in both directions before being relied
  on: it reports the base standard's own `example_G1.mpd`,
  `example_G10.mpd` and `example_G23.mpd` as valid, and reports seven
  deliberately malformed documents as invalid (zero `<Period>`;
  `Event@messageData`; an undeclared DASH-namespace element; a missing
  `MPD@profiles`; a foreign attribute on `<EventStream>`; a foreign child
  on `<ImportedMPD>`; `<EssentialProperty>` on `<Period>`).
- The 14 examples declaring the List or Single-Period-Static profile were
  additionally checked against the profile rules of DASH §8.14 and
  DASH §8.15.2 / §8.15.3 mechanically; all 14 pass, and the same checker
  reports a violation when a known-good example is mutated to break one
  rule.
- Each construct assessed Conforming / Marginal / Non-conforming.

## Base-standard findings (highlights)

- **Annex B is reachable and settles both of the v8 audit's open schema
  questions.** `DASH-MPD.xsd` declares exactly one global element,
  `<xs:element name="MPD" type="MPDtype"/>`. `ImportedMPD` and
  `EventStream` exist only as local declarations inside `PeriodType`, so
  at a position inside a foreign-namespace parent there is no declaration
  for a `lax` processor to find and the element is skipped. The
  candidate's §5.5.2 note that *"@schemeIdUri's required use, the typing
  of @presentationTime and @id, and the prohibition on @messageData are
  not enforced by schema validation there"* is now demonstrated rather
  than argued: a `<EventStream bogusAttr="1" messageData="x">` inside
  `<svta:Candidate>` validates, while the identical element one level up
  inside `<Period>` is rejected.
- **The four v8 remedies were re-derived independently and all four hold.**
  M1's §8.1 permission, M2's and M3's placements, and the §8.1
  Interoperability-Point recommendation are each quoted above from the
  primary copy. On M1 the base standard says *"It is recommended that
  such external definitions be not referred to as profiles, but as
  Interoperability Points"* — a recommendation, and §4.7.8 records the
  divergence with its reason, which is the correct handling.
- **M4 is confirmed as a defect in the base text, not in the candidate.**
  DASH §8.14 opens *"The ISO-BMFF List profile is an extension of the
  ISO-BMFF CMAF Profile (see subclause 8.12)"*, and DASH §8.12 defines
  two: the DASH CMAF Core Profile (§8.12.5, `urn:mpeg:dash:profile:cmaf:2019`)
  and the DASH CMAF Extended Profile (§8.12.6,
  `urn:mpeg:dash:profile:cmaf-extended:2019`). Nothing in §8.14 names
  which. The inherited constraint set is genuinely undetermined.
- **The base standard answers one question the candidate carries as open.**
  DASH Table 63 states *"If the value of @maxDuration is zero, the event
  is not executed"*, and *"If absent, the value is assumed to be
  infinity"*. The candidate binds its own `@maxDuration` to those
  semantics and then lists the meaning of zero as unresolvable.
- **Two general `<Event>` rules the candidate does not restate.** DASH
  Table 44: `@presentationTime` is *"relative to the start of the Period,
  taking into account the @presentationTimeOffset of the Event Stream"*;
  `@duration`'s *"interpretation … is defined by the scheme owner"*; and
  *"NOTE Per 5.10.4.5.3, the scope of an MPD event appearing in one
  Period is that Period, and its active interval never 'spills over' to
  any other Period."* The second sentence is what licenses the
  candidate's window semantics; the third bounds them and is absent.

## Non-conforming items detail

### N1 — The `PlayList` metric declaration is schema-invalid on two counts

**Where**: §5.9 (the normative snippet), Annex E.2 (`<Metrics>` in the
main MPD), Annex H.2 (same). Three occurrences.

The candidate authors:

```xml
<Metrics metrics="PlayList" reportingInterval="PT60S">
  <Range starttime="PT0S"/>
</Metrics>
```

**Conflict 1 — `@reportingInterval` does not exist.** `MetricsType`
declares one attribute, `<xs:attribute name="metrics" type="xs:string"
use="required"/>`, plus `<xs:anyAttribute namespace="##other"
processContents="lax"/>`, which by definition excludes the DASH
namespace an unprefixed attribute lands in. DASH Table 42 lists
`@metrics`, `Range`, `@starttime`, `@duration` and `Reporting` and
nothing else. The string `reportingInterval` appears **zero** times in
the whole primary copy; the same extraction returns 63 hits for
`Reporting`, 5 for `Metrics element` and 4 for `PlayList`, so the zero is
the document's and not the search's.

**Conflict 2 — `<Reporting>` is mandatory and is missing.** The schema
declares `<xs:element name="Reporting" type="DescriptorType"
maxOccurs="unbounded"/>` with `minOccurs` omitted, so it defaults to 1.
DASH Table 42 states the same: `Reporting` is `1 ... N`,
*"specifies information about the requested reporting method and
formats."* DASH §5.9.1 confirms the intent — the `<Metrics>` element
carries *"the list of DASH Metrics …, the time interval and the
granularity for the measurements, as well as the scheme according to
which the metric reporting is desired."*

**Measured**: the two annex manifests are the only 2 of the candidate's
49 full-MPD examples that fail Annex B validation, and both fail on
exactly these two errors. Wrapping the §5.9 snippet in an otherwise
valid MPD reproduces them; the same wrapper with `@reportingInterval`
dropped and one `<Reporting>` added validates.

**Suggested fix**: remove `@reportingInterval` and add a `<Reporting>`
descriptor, for example

```xml
<Metrics metrics="PlayList">
  <Range starttime="PT0S"/>
  <Reporting schemeIdUri="urn:mpeg:dash:reporting:scheme"/>
</Metrics>
```

This interacts with the candidate's own position that *"How a
measurement reaches anyone is out of scope"*: DASH does not let a
`<Metrics>` element decline to name a reporting scheme, so either §5.9
names one (or names the Publisher's choice as an authoring obligation),
or it stops emitting a `<Metrics>` element and states the derivation
without the carrier. The out-of-scope stance is defensible; the
document that declares the metric while omitting `<Reporting>` is not.

## Marginal items detail

### M1 — `@maxDuration` narrowed to required, against an inherited semantic the candidate leaves open

`@maxDuration` on `<svta:OverlayPresentation>` and
`<svta:PauseAdPresentation>` is declared required, and the candidate
states *"Name, units and termination semantics are those of
`@maxDuration` in DASH §5.16.5.2."* That clause fixes two boundary
values: *"If absent, the value is assumed to be infinity"* and *"If the
value of @maxDuration is zero, the event is not executed."* The
candidate's refinement-gap #6 nonetheless records "what a zero
`@maxDuration` means on a pause-trigger window" as unresolvable, and its
open-point table records the absent case as a divergence from the base
default — correctly, since the attribute is required here.

The ambiguity is that a reader cannot tell whether the inheritance
clause carries the zero rule or not, and the two readings differ by
whether a resolution request is issued at all.

**Suggested clarification**: state explicitly that `@maxDuration="0"`
means the slot yields no ad and no resolution request is issued, per
DASH Table 63, or state explicitly that the zero case is excluded from
the inheritance. Either closes it; leaving the inheritance clause
unqualified next to an open point is what does not.

### M2 — `ListMPD` inherits an unidentified constraint set (carried from v8 M4)

DASH §8.14: *"The ISO-BMFF List profile is an extension of the ISO-BMFF
CMAF Profile (see subclause 8.12), with the following requirements
overriding the requirements of the latter subclause"*, followed by five
rules. DASH §8.12 defines two profiles (§8.12.5 Core, §8.12.6 Extended)
over a common body of constraints in §8.12.4. Which one a `ListMPD`
inherits is not stated, and §8.12.5 adds Period-boundary restrictions
that §8.12.6 does not.

The candidate's use of `ListMPD` satisfies all five §8.14 rules, checked
mechanically across its 7 ListMPD examples. What cannot be decided is
whether those examples satisfy the inherited §8.12 constraints, because
the inherited set is unidentified in the base text.

**Suggested clarification**: unchanged from v8 — this is a working-group
question for the base standard's maintainers, not a wording fix. The
candidate already carries it as refinement gap #17. Recommend raising it
as a defect report against DASH §8.14 rather than resolving it here.

### M3 — The beacon timebase re-anchors a baseline attribute the base standard anchors to the Period

DASH Table 44 fixes `Event@presentationTime` as *"the presentation time
of the event relative to the start of the Period, taking into account
the @presentationTimeOffset of the Event Stream, if present"*. The same
table delegates only `@duration`'s interpretation to the scheme owner,
not `@presentationTime`'s anchor.

Inside a sub-MPD `<Period>` the two coincide, because the Period is the
ad. Inside `<svta:Candidate>` there is no Period, so the base standard's
anchor has no referent and §5.5.3 supplies one — *"relative to the start
of the ad's own presentation"*. That is the only workable reading, and
it is unreachable by a client that predates this specification, so
nothing observable breaks. But it is an attribute of the DASH namespace
being read against an origin the DASH namespace does not define there.

**Suggested clarification**: say so in §5.5.3 — that at the
`<svta:Candidate>` position the base standard's Period anchor has no
referent and this specification defines the origin, which is why the
same attribute means the same thing in both carrier positions. One
sentence; it turns a silent redefinition into a stated one.

### M4 — The empty linear resolution document (carried from v8 M5)

A `ListMPD` carrying one `<Period duration="PT0S"/>` and no
`<ImportedMPD>`. It is schema-valid (verified), satisfies all five
§8.14 rules (verified), and satisfies DASH Table 4's Adaptation Set
exemption at zero duration (verified). The MPD-conformance ladder of
DASH §8.1 does not require a Representation — that requirement sits on
the *Media Presentation* ladder: *"A Media Presentation is conforming to
profile ProfA when … 2) There is at least one Representation in each
Period in the profile-specific MPD for ProfA."* The candidate's position
that a resolution document is an MPD used as a carrier rather than a
Media Presentation is therefore well grounded.

What remains undecidable is the inherited §8.12 Period constraints,
which is M2. The verdict is Marginal for that reason alone and not
because anything in §8.14 or §8.1 is violated.

**Suggested clarification**: none available until M2 resolves. Recommend
the candidate record explicitly that the empty ListMPD clears every
constraint the base text identifies, and that only the unidentified
inherited set is open — which is a narrower and more useful statement
than "unresolvable".

### M5 — The opportunity window is not bounded to its declaring Period

§5.1.3 and §5.1.4 define the window as the parent `<Event>`'s
`@presentationTime` and `@duration`, and nothing in the candidate states
the base standard's bound: DASH Table 44, *"NOTE Per 5.10.4.5.3, the
scope of an MPD event appearing in one Period is that Period, and its
active interval never 'spills over' to any other Period."*

A Publisher can therefore author an overlay window whose nominal end
falls past the end of the declaring Period, and two conformant
implementations will disagree about whether the window is truncated at
the Period boundary — one following the candidate's definition, one
following the base standard's NOTE. This is adjacent to, but not the
same as, refinement gap #4 (whether a presentation may outlive the
`@duration` that declared its window); that gap is about the cap, this
is about the window itself.

**Suggested clarification**: state in §5.1 that an opportunity window is
bounded by the end of its declaring `<Period>`, citing DASH Table 44,
and say what a Publisher authors when an opportunity has to straddle a
Period boundary (two events, one per Period).

### M6 — The cited basis for the two nested baseline elements is not the clause that licenses them

§5.3.4 and §5.5.2 both rest the placement of a DASH-namespace element
inside an SGAI parent on the removal rule of DASH §5.2.1: *"The MPD
shall be authored such that, after XML attributes or elements in the
DASH namespace but not in the XML schema documented in Annex B are
removed, the result is a valid XML document formatted according to that
schema and that conforms to this document."*

That rule does not reach these two constructs. `EventStream` and
`ImportedMPD` **are** in the Annex B schema — they are declared inside
`PeriodType` — so the rule's own predicate ("not in the XML schema")
does not select them, and the sentence immediately preceding it scopes
the case it is written for: *"The extension of the DASH XML schema … in
particular the addition of XML attributes or elements in the DASH
namespace, is reserved to ISO/IEC."* The rule covers ISO's own future
additions, not a third party reusing an existing element at a position
where it is not declared.

What actually licenses both placements is the mechanism §5.3.4 already
states and tags `[inferred]`: the schema declares exactly one global
element, so at a position reached only through a `##other` wildcard with
`processContents="lax"` there is no declaration to validate against and
the element is skipped. Verified against the schema and demonstrated by
validation. The separate obligation — that stripping the foreign
namespace leaves a valid document — is the *second* paragraph of
DASH §5.2.1 and is satisfied, also verified.

The outcome does not change: both constructs are Conforming. The cited
reason does.

**Suggested clarification**: in §5.3.4 and in the §5.5.2 note, replace
the removal-rule basis with the lax-wildcard basis, drop the
`[inferred]` tag now that Annex B has been read, and keep the second
paragraph of DASH §5.2.1 as what it is — the removal obligation the
construct satisfies, not the permission it rests on.

## Open questions surfaced

None. Every construct in the inventory has a governing clause located in
the primary copy or in the Annex B schema the primary copy points at. No
item is logged `[fetch-failed]`.

Two items are open against the **base standard** rather than against the
candidate, and both are recorded above: M2 (DASH §8.14's unnamed CMAF
parent) and, downstream of it, M4.
