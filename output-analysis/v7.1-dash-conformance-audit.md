# DASH conformance audit — v7.1 (2026-09-16)

**Audit target**: `output/v7.1-sgai-spec.md` (4763 lines; chapters 1–8,
Annexes A–N, trailing `## Refinement gaps` table).
**Reference**: MPEG-DASH 6th edition, **ISO/IEC 23009-1:2026(en)**, Sixth
edition, 2026-07. Referred to below as *the base specification*.
**Method**: inventory of every new or modified construct + per-construct
verdict grounded on verbatim clause and schema text + a mechanical
element-order check of all 31 XML examples against the base schema's
`xs:sequence` declarations.

## Scope

This is a conformance audit against the base specification only. Internal
design coherence, requirement traceability and editorial quality are out of
scope. No prior sidecar for v7 or v7.1 was read; the `## Refinement gaps`
table inside the audited document was read, because it is part of the
artefact under audit.

## Method summary

- Inventory built from §2.1 (URI registry), §4.7 (extension points and the
  per-construct backward-compatibility audit), §5.1–§5.8 (syntax), §5.2.3
  (degenerate documents), and every `xml` example in Annexes A–M.
- 24 constructs assessed. Each verdict cites the base clause or schema
  fragment it is measured against, quoted inline.
- A mechanical check was run over all 31 XML examples in the spec, validating
  well-formedness and child-element order against the four base `xs:sequence`
  declarations the examples touch: `MPDtype` (§5.3.1.3), `PeriodType`
  (§5.3.2.3), `EventStreamType` and `EventType` (§5.10.2.3). Result and
  negative control in **Annex — instrument**.

## Findings from the primary source (highlights)

- **§5.2.1 is the load-bearing extension rule and the spec uses it correctly.**
  Verbatim: *"the MPD shall be authored such that, after XML attributes or
  elements in the other namespaces than the DASH namespace are removed, the
  result is a valid XML document formatted according to that schema and that
  conforms to this document."* Stripping every `svta:` element from the
  Overlay Resolution Document leaves `<Period id="resolution"
  duration="PT0S"/>`, which validates. The sibling-vs-nested authoring lever
  of §4.7.1 is a sound reading of the same clause.
- **The same clause bounds how far reuse of baseline elements can go.**
  Verbatim: *"The extension of the DASH XML schema (as provided in Annex B),
  in particular the addition of XML attributes or elements in the DASH
  namespace, is reserved to ISO/IEC."* The schema declares exactly one global
  element, `<xs:element name="MPD" type="MPDtype">`; every other element,
  `ImportedMPD` and `EventStream` included, exists only as a local
  declaration inside a complex type. This is what makes M1 and M2 real rather
  than cosmetic.
- **§5.16.2.2.5 step 2d is a genuine fallback chain, exactly as §4.6.8
  claims** — *"If execution fails, steps a-c above are repeated for next
  events in QE"* — and §5.16.2.2.6 states the failure conditions the
  specification then narrows: *"Execution fails if at least one of the
  conditions below is true at PRTA: — APDA is determined to be 0. … —
  Alternative MPD is a List MPD, and merge process resulted in no available
  media."*
- **§8.1 has two distinct conformance ladders**, and the spec's degenerate
  documents satisfy the MPD ladder but not the Media Presentation one:
  *"A Media Presentation is conforming to profile ProfA when it satisfies the
  following: … 2) There is at least one Representation in each Period in the
  profile-specific MPD for ProfA."*
- **Annex I.3.1 permits the `<RequestParam>` placement the spec chose**,
  verbatim: *"The RequestParam element(s) may be present in elements such as
  but not limited to MPD, Period, AdaptationSet, Representation,
  Preselection, or EventStream."* Table I.4 then scopes `altmpd` to *"all
  requests for MPDs representing the alternative Media Presentation, as
  defined in subclause 5.16"*, and provides the escape hatch the spec does
  not use: *"`<URN / tag URI>` — a URN or tag URI, where the request type
  semantics is understood by the client and specified by the URN / tag URI
  owner."*
- **Every "considered and not reused" justification in §5.1.6, §5.3 and §5.6
  checks out against the source.** `@selectionPriority` is
  `xs:unsignedInt default="1"` and *"higher numbers are the preferred
  selection over lower numbers"* (§5.3.5.2), so the spec is right that it
  inverts document order. `urn:mpeg:dash:fallback:2016` (§5.11.3) states
  *"the content author expresses the preferences of using one of those by the
  order with the first one having the highest preference"* at whole-MPD
  granularity, which is the spec's cited precedent and the correct clause
  number — the base's own URI index at the front of the document mis-cites it
  as §5.11.2. Annex L.3.4.2 does split the construct the way §5.1.4 claims:
  *"the Event@presentationTime and Event@duration attributes are used to
  indicate the start and the duration of the selection window"*, with the
  interaction resolved off-timeline via `SelectionInfo@contactURL`. And the
  base does model a pause only as a metrics record — Table of playout
  metrics, `starttype` = *"Resume - Resume from pause"*.
- **§4.6.9's live pause-freeze ceiling is correctly bounded.** §5.16.2.1
  step 5 and Table 61's NOTE 2 on `@returnOffset` both state the trimming the
  spec inherits: *"if RT is in the past, the playback shall start from the
  oldest available media segment (the edge of the timeshift buffer). …
  NOTE 2 The above can happen in case a user pauses the alternative Media
  Presentation."*

## Non-conforming items detail

### NC1 — §4.6.8 narrows a §5.16.2.2.6 failure condition on the *inherited* schemes

**Spec section**: §4.6.8, and §5.2.3 (the linear empty `ListMPD`).
**Base clause**: §5.16.2.2.6 (Execution) with §5.16.2.2.5 step 2 (playhead-triggered processing).

The base specification says, verbatim:

> Execution fails if at least one of the conditions below is true at PRTA:
> — APDA is determined to be 0.
> …
> — Alternative MPD is a List MPD, and merge process resulted in no available media.

and §5.16.2.2.5 step 2d:

> If execution fails, steps a-c above are repeated for next events in QE, until: — Execution succeeds, or — PRT of the topmost event in the queue is in the future …, or — The queue is empty.

§4.6.8 declares the divergence openly: the Player falls through to a
subsequent overlapping window only when it **cannot access** the first
window's resolution document, and *"a `200` carrying a resolution document
with no candidates is **accessible** … and leaves the remaining windows
untouched."*

The conflict is real and it is confined to the **linear** family, because
that family rides the baseline `urn:mpeg:dash:event:alternativeMPD:insert:2025`
and `:replace:2025` schemes, whose execution semantics the base owns. The
empty `ListMPD` of §5.2.3 — one `<Period id="no-fill" duration="PT0S"/>` with
no `<ImportedMPD>` — is precisely a List MPD whose merge yields no available
media, so a base-conformant client fails the execution and proceeds to the
next queued event, while an SGAI-conformant Player stops. Two Players reading
the same document with the same scheme URI behave differently. That is a
conformance deviation, not an extension.

**Suggested fix**: scope the narrowing to the two SGAI schemes, whose
semantics this specification owns, and leave the baseline schemes' execution
model untouched. Then §5.2.3's linear no-fill needs a different encoding —
an HTTP `204`, or a `ListMPD` carrying a zero-length Period the Player is
told to treat as answered — so the "unfilled vs unresolvable" distinction
survives without redefining an inherited scheme. The document already
carries this as gap #18 / #6, so what is missing is the decision, not the
diagnosis.

### NC2 — §5.5.2's tooling note misstates where the base places `<EventStream>`

**Spec section**: §5.5.2, the blockquoted "Note for tooling".
**Base clause**: §5.3.1.3 (`MPDtype` XML syntax) and §5.3.2.3 (`PeriodType`).

The note says:

> The base specification places `<EventStream>` as a child of `<Period>` or of `<MPD>`.

The `MPDtype` `xs:sequence` contains no `EventStream` particle. Its full
child list is `ProgramInformation`, `BaseURL`, `Location`, `PatchLocation`,
`RequestParam`, `ServiceDescription`, `InitializationSet`,
`InitializationGroup`, `InitializationPresentation`, `ContentProtection`,
`Period`, `Metrics`, `EssentialProperty`, `SupplementalProperty`,
`UTCTiming`, `LeapSecondInformation`, `ContentSteering`, then
`<xs:any namespace="##other"/>`. The string `name="EventStream"` occurs
exactly once in the whole schema, inside `PeriodType`. §5.2.3.2 lists the
element as `Period.EventStream` among the additions of the second edition,
with no MPD-level counterpart.

Consequence: a tooling author who follows the note scans `<MPD>` children for
callback event streams, finds none there ever, and — worse — an authoring
tool built on the same sentence emits an MPD-level `<EventStream>` that does
not validate.

**Suggested fix**: replace with *"The base specification places
`<EventStream>` only as a child of `<Period>` (§5.3.2.3)."* The rest of the
note — that a validator scanning only canonical placements misses the
carrier attached to a non-video candidate — stands unchanged and is the
point worth keeping.

## Marginal items detail

### M1 — a callback `<EventStream>` inside `<svta:Candidate>` is laxly skipped, not validated, and sits outside the scheme's dispatch scope

**Spec section**: §5.5.2, §5.2.2.4.
**Base clause**: §5.10.2.2 (Event semantics, the Period-scope NOTE), §5.10.4.5.3, §5.2.1.

Two independent effects, both real, neither fatal:

1. **It cannot be schema-validated in that position.** Inside
   `<svta:Candidate>`, validation proceeds under
   `processContents="lax"`. A lax processor validates only elements for
   which it can find a declaration; the MPD schema declares `EventStream`
   only locally inside `PeriodType`, and §5.2.1 reserves the addition of
   elements in the DASH namespace to ISO/IEC, so the SVTA schema cannot
   supply a global declaration for it. The element is therefore skipped —
   `value`, `timescale` and each `Event@presentationTime` go unchecked.
2. **It sits outside the scheme's declared scope.** §5.10.2.2 carries the
   NOTE: *"Per 5.10.4.5.3, the scope of an MPD event appearing in one Period
   is that Period, and its active interval never 'spills over' to any other
   Period."* A callback stream that is in no Period has no scope under the
   base model, and §5.5.3 re-bases its `@presentationTime` origin onto the
   ad's own presentation — a timebase the base scheme does not define.

**Suggested clarification**: state explicitly in §5.5.2 that the
candidate-level carrier reuses the callback scheme's *syntax and firing
behaviour* while this specification supplies its scope and timebase, and that
it is validated by the SGAI schema rather than by the DASH schema. If a
future edition wants full validatability, the carrier becomes a
`urn:svta:`-namespace element that mirrors the callback shape.

### M2 — `<ImportedMPD>` inside `<svta:RenderableAsset>` reuses the syntax but not the processing model

**Spec section**: §5.3.4.
**Base clause**: §5.3.2.6.1 / Table 4 / §5.3.2.6.3.

§5.3.4 asserts *"§5.3.2.6 does not constrain the parent of `<ImportedMPD>`"*
and *"A schema for `<svta:RenderableAsset>` admits the core-namespace
`<ImportedMPD>` as a first-class child."* Three things qualify that:

- Table 4 declares the element as `Period.ImportedMPD` with the constraint
  *"This element shall not appear if the value of `MPD@type` is not 'list'."*
  The Overlay Resolution Document declares `type="static"`. The constraint is
  written against the Period child, so the spec is not in breach — but the
  reuse is not as unconstrained as the sentence implies.
- §5.3.2.6.1: *"Linked Periods are indicated by the ImportedMPD element in a
  Period element."* The whole reference processing model of §5.3.2.6.3 —
  resolve, merge `@profiles`, move MPD-level descriptors to Period level,
  and on failure *"the ImportedMPD element is removed, and consequently the
  Linked Period becomes a regular Period"* — presupposes a Period. Inside
  `<svta:RenderableAsset>` there is none, so none of it applies and this
  specification silently supplies its own resolution semantics.
- The "first-class child" claim needs a global element declaration that does
  not exist (see M1, effect 1), and §5.2.1 forecloses creating one.

**Suggested clarification**: keep the element, and add one sentence to §5.3.4
saying that this specification reuses `<ImportedMPD>`'s *syntax and its
Single-Period-Static binding* and defines its own resolution semantics in
this parent, the §5.3.2.6.3 merge model being inapplicable where there is no
Linked Period; and drop the "first-class child" claim in favour of stating
that the SGAI schema admits it via a lax wildcard over the DASH namespace.
(Carried in the document as gap #20.)

### M3 — `altmpd` does not name a non-linear resolution request

**Spec section**: §5.8.1 (and §5.8 opening, which frames both families).
**Base clause**: Annex I.3.6, Table I.4.

Table I.4 defines `altmpd` as *"all requests for MPDs representing the
alternative Media Presentation, as defined in subclause 5.16"*. A linear
slot's resolution request is exactly that, so the §5.8.1 example — which
uses `<InsertPresentation>` — is correct. An overlay or pause-ad resolution
request is issued against `<svta:OverlayPresentation>@uri` /
`<svta:PauseAdPresentation>@uri` and is not a §5.16 request, so `altmpd` does
not select it and the Publisher's query template silently does not travel.

The base supplies the mechanism the spec would need, in the same table:
*"`<URN / tag URI>` — a URN or tag URI, where the request type semantics is
understood by the client … The client shall drop unknown URIs from the
`@includeInRequests` and `@includeInHeaders` strings prior to processing
them"* — which also means an unknown URI degrades safely on a legacy client.

**Suggested clarification**: mint one request-type URI for the non-linear
resolution request, register it in §2.1 alongside the other URIs, and state
in §5.8.1 that `altmpd` covers linear slots while the new URI covers overlay
and pause-ad slots. (Carried as gap #22.)

### M4 — `<svta:Click>` on a list-profile-only `ListMPD` is removed by the profile-conformance procedure

**Spec section**: §5.6.1, "Note on profile signalling".
**Base clause**: §8.1, profile-specific MPD construction, step 4.

Verbatim: *"All elements or attributes that are either (i) in this document
and explicitly excluded by ProfA, or (ii) **in an extension namespace and not
explicitly included by ProfA**, are removed from the profile-specific MPD."*

The spec states the consequence accurately and does not resolve it: a
`ListMPD` whose `@profiles` names only `urn:mpeg:dash:profile:list:2024` has
its `<svta:Click>` stripped for conformance checking, and a client bound to
that profile alone may drop it. The result is that §4.6.11's "every
conformant Player fires the click identically" does not hold for linear ads
carried on a list-profile-only document.

**Suggested clarification**: mint a linear-side SGAI profile URI that
explicitly includes the `urn:svta:dash:sgai:2026` namespace, and require the
APS to declare it alongside `list:2024` on any `ListMPD` carrying
`<svta:Click>`. §2.1 currently mints a profile URI for the non-linear
document only. (Carried as gap #21.)

### M5 — the zero-duration Period satisfies §5.3.2.2 but not §8.1's Media-Presentation rule

**Spec section**: §5.2.2.1 and §5.2.3 (both document families).
**Base clause**: §5.3.2.2 Table 4 vs §8.1.

The spec's argument is correct as far as it goes. Table 4, verbatim:
*"At least one Adaptation Set shall be present in each Period unless the
value of the `@duration` attribute of the Period is set to zero."* Declaring
`duration="PT0S"` discharges it, and `Period` is declared
`<xs:element name="Period" type="PeriodType" maxOccurs="unbounded"/>` with
`minOccurs` omitted — so zero Periods would indeed not validate. Both claims
in §5.2.3 check out verbatim.

What the argument does not reach is the second ladder in §8.1: *"A Media
Presentation is conforming to profile ProfA when it satisfies the following:
1) The MPD of the Media Presentation is conforming to profile ProfA … 2)
There is at least one Representation in each Period in the profile-specific
MPD for ProfA."* Neither resolution document has a Representation in its
Period, so each is a conforming **MPD** but describes a non-conforming
**Media Presentation**. This is arguably the intended reading — §8.14 itself
notes List MPDs *"are not expected to be an 'entry point' to a service"* —
but the spec asserts document conformance without distinguishing the two
ladders, and a conformance checker implementing §8.1 literally will flag both
documents.

**Suggested clarification**: one sentence in §5.2.2.1 and §5.2.3 recording
that a resolution document is a conforming MPD used as a carrier and is not
itself a Media Presentation, so §8.1's per-Period Representation rule does
not apply to it. This is a scoping statement, not a change of shape.

### M6 — §5.1.2 restates `<ReplacePresentation>` without two of its inherited co-constraints

**Spec section**: §5.1.2.
**Base clause**: §5.16.5.2 Table 63 (`@clip`), §5.16.4 Table 61
(`@startWithOffset`), §5.16.2.2.6.

Every attribute name, type and default in §5.1.2's table matches §5.16.6
exactly. Two conditional restrictions stated in the base prose are not
carried over:

- `@clip`: *"This attribute shall not be present if the `@maxDuration`
  attribute is absent."* Moot in practice here, since §4.3.2 makes
  `@maxDuration` mandatory — but the spec presents the table as the
  authoring reference.
- `@startWithOffset`: *"This attribute does not apply to a live alternative
  presentation and shall not be used if the `@clip` attribute value is
  'false'."* Reinforced in §5.16.2.2.6: *"When alternative media presentation
  is a live presentation, it always starts at the live edge, and
  `@startWithOffset` attribute shall not be present."* Since
  `<ReplacePresentation>` is the construct §5.1.1 routes live content to,
  this one bites.

The spec says the element is *"Reused verbatim from §5.16.4"*, so the
constraints are inherited in principle. The risk is an implementer authoring
from the table alone.

**Suggested clarification**: add the two conditions to the Description cells,
or add one line under the table stating that all conditional restrictions of
§5.16.4 and §5.16.5.2 apply unchanged.

## Open questions surfaced

- **Whether the SGAI XML schema exists as an artefact.** Several verdicts
  (C9–C14, M1, M2) turn on `processContents="lax"` behaviour, which differs
  depending on whether a validator can load a schema for
  `urn:svta:dash:sgai:2026`. The specification describes the elements but
  references no schema document. This is not a base-specification
  non-conformance; it is the thing that decides whether the resolution
  document is machine-checkable at all.
- **Whether `<svta:Candidate>@duration` (`xs:duration`) and slot
  `@maxDuration` (`@timescale` units) can be compared without a stated
  conversion rule.** Purely internal, so out of scope for this audit; noted
  because a conformance checker has to do the arithmetic.
- **`MPD@type` on the Overlay Resolution Document.** The spec declares
  `static`. Whether `list` would be the better signal — given §5.3.1.4's
  *"For Media Presentations with MPD@type set to 'list' the constraints of a
  static Media Presentation shall apply"* and the fact that `ImportedMPD`
  under a Period requires `type="list"` — is a design choice, not a
  conformance defect, and is not decided here.

## Annex — instrument

The XML examples were checked mechanically rather than by eye. The checker
parses every ```` ```xml ```` block in the spec, then walks each element whose
type is one of the four base `xs:sequence` declarations the examples touch,
asserting that child elements appear in the schema's declared particle order
and that no undeclared DASH-namespace child is present. Foreign-namespace
children are positioned at the `<xs:any namespace="##other"/>` particle, which
is last in all four types.

```
$ python3 check.py output/v7.1-sgai-spec.md
BLOCKS CHECKED: 31
  no ordering/well-formedness findings
```

A zero is only a result if the instrument can produce a non-zero. Negative
control: five deliberately broken blocks, one per failure mode the checker
claims to detect.

```
$ python3 check.py negctl.md
BLOCKS CHECKED: 5
  FAIL line 1: <Period> child order violates xs:sequence: <EventStream> appears after <AdaptationSet>
  FAIL line 10: <Period> child order violates xs:sequence: <EventStream> appears after <{urn:svta:dash:sgai:2026}OverlayList>
  FAIL line 19: <Period> has child <Bogus> not declared in PeriodType sequence
  FAIL line 24: NOT WELL-FORMED: mismatched tag: line 2, column 66
  FAIL line 27: <Event> child order violates xs:sequence: <InsertPresentation> appears after <{urn:svta:dash:sgai:2026}X>

Reading: all 31 examples in v7.1 are well-formed and respect the base schema's
element ordering, including the three orderings that are easy to get wrong —
`ImportedMPD` first inside `PeriodType`, `EventStream` before `AdaptationSet`,
and the scheme-specific child before any foreign-namespace sibling inside
`EventType`. The checker does **not** validate attribute values, cardinality,
or anything inside a `urn:svta:` subtree; those are covered by the
per-construct verdicts above.
